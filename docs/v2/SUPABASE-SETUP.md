# Supabase PostgreSQL foundation

The Prisma 7 PostgreSQL foundation is hosted by Supabase. The checked-in migrations create identity tables (`users`, `sessions`), India-only user-owned `addresses`, and V2 commerce tables for catalog, inventory, carts, coupons, orders, payments, reservations, and admin audit. A later migration removes the retired OTP and pending-admin bootstrap tables. The legacy application continues to use MongoDB until each domain is migrated and cut over.

## Runtime requirements

- Use Node.js `20.19.x` (see `.nvmrc`). Prisma 7 supports Node 20 starting at 20.19.
- Copy `.env.example` to the ignored `.env.local` and fill in the Supabase values locally. Never commit `.env.local` or paste credentials into source files.
- `DATABASE_URL` is used by the runtime Prisma client. For a long-running Next.js server, use the Supavisor **session pooler** (port 5432). For serverless runtime, use the Supavisor **transaction pooler** (port 6543) and include `pgbouncer=true` as Supabase directs.
- `DIRECT_URL` is used only by Prisma CLI migrations. Use the Supabase direct database connection when the environment supports its network route; otherwise use Supavisor session mode. Do not use the transaction pooler for schema migrations.

The project’s `.env.example` contains placeholders, not working credentials. Supabase Dashboard → **Connect** provides the project-specific values. Keep the database password URL-encoded when it contains reserved URL characters.

## Commands

```sh
npm ci
npm run db:validate
npm run db:generate
npm run db:migrate:deploy
npm run db:status
npm run db:seed
npm run build
```

`db:migrate:deploy` applies checked-in migrations and does not reset the database. `db:migrate:dev` is intended for local development and may prompt for migration creation; do not point it at production. Migrations enforce E.164 user phone format, India address phone/PIN/country constraints, and at most one default address per user. The latest migration removes the retired OTP and pending-admin bootstrap tables.

The Prisma configuration loads `.env.local` (then `.env`) because Prisma CLI does not use Next.js environment loading. `prisma.config.js` points migrations at `DIRECT_URL`; the application adapter reads `DATABASE_URL`. The build script generates the ignored Prisma client before compiling, so build environments must provide `DIRECT_URL` even though generation itself does not connect to the database.

## Seed and authentication

The regular seed is deliberately inert unless `DEV_SEED_CUSTOMER_PHONE` is set. It can only create an `ACTIVE` `CUSTOMER` fixture and refuses to run when `NODE_ENV=production`. It never provisions an admin. V2 has no login/session-creation flow; use the active legacy admin login for current operations.

## Current migration boundaries

- PostgreSQL schema contains identity, admin-bootstrap audit, user address, and V2 commerce records.
- V2 API routes use the app-level Prisma client; existing legacy routes and storefront flows still use MongoDB.
- No migration, connection, or constraint integration check has been run against the Supabase project yet; those require valid project connection strings in `.env.local`.
- Prisma-generated code is ignored and regenerated by `npm run db:generate`.
